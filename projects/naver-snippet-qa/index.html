네이버 스니펫 오픈도메인 QA

검색 결과에 뜨는 스니펫은 문장이 중간에서 잘려 있습니다. 그 조각글에서 답을 찾아내는 한국어 QA 모델을 만들었습니다. 학습 데이터의 90%에 아예 답이 들어 있지 않다는 것이 가장 큰 벽이었습니다.

기간
2020
역할
데이터 분석 · 증강 전략 설계 · 모델 ablation 및 앙상블
스택
PyTorch BERT KoELECTRA KorQuAD
코드
PIRL-korquad-open-cs492h ↗ (새 탭에서 열림)

문제

오픈도메인 QA 과제이지만 데이터가 특이했습니다. 네이버 검색 결과로 나타나는 스니펫을 그대로 쓰기 때문에, SQuAD나 KorQuAD처럼 잘 다듬어진 문단이 주어지지 않습니다. 모델은 이 조각글 안에서 답을 찾아내야 합니다.

데이터를 열어 보니 두 가지가 걸렸습니다.

  • 극단적인 불균형. 학습 데이터의 90%가 unanswerable — 주어진 스니펫 안에 정답이 아예 존재하지 않았습니다.
  • 끊긴 문장. 스니펫은 문장이 완성되어 있지 않아, 모델이 전체 맥락을 잡기 어렵습니다.

질문 유형도 한쪽으로 쏠려 있었습니다. Who · When · What · Where 같은 단답형이 대부분이었고, How와 Why는 100개도 되지 않았습니다.

접근

1. 두 종류의 데이터 증강

두 문제에 각각 다른 처방을 붙였습니다.

답이 없는 질문에는 맥락을 되찾아 줬습니다. 스니펫이 잘려 나가면서 정답까지 함께 잘려 나간 경우가 많았습니다. 그래서 스니펫의 출처 url을 따라가 원문 context를 검색해 오고, 그 내용으로 지문을 보강(amplify)했습니다. 예를 들어 세종대왕에 관한 질문의 정답이 1397년 5월 7일인데 스니펫에는 그 대목이 잘려 있다면, 원문에서 해당 부분을 찾아 지문에 되살리는 식입니다.

끊긴 문장에는 완성된 문장을 섞었습니다. KorQuAD 1.0에서 60,000개의 full-form QA pair를 가져와 학습 데이터에 보충했습니다. 온전한 문장으로 된 예시를 함께 보여주면, 모델이 일반적인 맥락을 이해하는 데 도움이 되리라는 판단이었습니다.

2. 사전학습 모델 비교와 앙상블

먼저 단일 모델로 ablation study를 돌렸습니다.

  • BERT-multilingual — 베이스라인
  • KoBERT, HanBERT, Electra
  • KoELECTRA — 가장 좋았습니다

그다음 variance를 줄이기 위해 앙상블 구성을 바꿔 가며 비교했습니다. KoELECTRA-base 단독, KoELECTRA-small v2 + distilKoBERT 조합, KoELECTRA-small v2 4개 묶음. 여기에 learning rate · optimizer · dropout을 조정했습니다.

결과

test score
36.0 → 41.9

BERT-multilingual 베이스라인이 36.0이었고, KorQuAD로 보강한 KoELECTRA-base-v2가 41.9로 마무리했습니다.

여기서 읽을 수 있는 것은 모델을 바꾼 것보다 데이터를 바꾼 쪽이 결정적이었다는 점입니다. KoELECTRA로 갈아타는 것만으로는 36.0 → 36.5에 그쳤고, 같은 모델에 KorQuAD를 보강하자 41.9로 올랐습니다.

데이터 조합을 다섯 가지로 갈라 본 결과에서 한 가지가 눈에 띕니다. 증강을 많이 할수록 좋아지지는 않았습니다. 스니펫과 KorQuAD를 둘 다 증강한 조합은 오히려 KorQuAD만 더한 것보다 낮았고, 스니펫 쪽만 증강했을 때 가장 좋았습니다.

얻은 것

데이터 쪽에서. 결국 중요한 것은 모델에게 올바른 맥락을 담은 데이터를 주는 일이었습니다. 스니펫에 특화된 모델을 만든다고 해서 스니펫 데이터만 써야 하는 것은 아니었습니다. 스니펫 + KorQuAD, 스니펫 + SQuAD 조합이 모두 도움이 됐습니다. 다만 지문이 길다고 무조건 좋은 것도 아니었습니다 — 필요한 것은 길이가 아니라 일반적인 맥락이었습니다.

모델 쪽에서. 모델의 variance를 줄이는 일이 성능만큼 중요했습니다. 각 모델의 base 버전을 기준으로 ablation을 하고, 크기를 늘려 가며 확인한 뒤, 앙상블로 묶는 순서로 접근했습니다. 다만 앙상블을 키울수록 성능 향상 폭이 점점 줄어들었습니다. 모델을 키우는 수직적 확장과 여러 모델을 묶는 수평적 확장 사이의 trade-off를 어디서 끊을지가 실제 판단 지점이었습니다.

남은 질문

프로젝트를 끝내면서 가장 걸렸던 것은, url 원문을 일일이 검색해 지문을 보강하는 과정이 지나치게 번거롭다는 점이었습니다. 이 과정을 자동화할 수는 없을까. 모델에게 검색 기능을 쥐여 주고 url 원문을 스스로 읽어 오게 할 수는 없을까.

2023년에 이 페이지를 다시 열어 보며 덧붙인 메모 — “LLM을 사용한다면?”

지금은 그 질문에 해당하는 일을 하고 있습니다. 에이전트가 도구를 호출해 필요한 정보를 직접 가져오는 구조가, 그때 손으로 하던 일을 대신합니다.
