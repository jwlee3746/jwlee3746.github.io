**빠른 계층을 추가해도 거의 모든 요청이 깊은 계층으로 넘어가면, 사용자는 대기 단계만 하나 더 경험한다.** Fast·Deep 구조를 적용하면서 중요했던 것은 모델을 두 개 두는 일보다 처리 책임과 승격 기준을 명확히 하는 일이었다.

이 글은 OpenClaw 실험 이후 디바이스 어시스턴트의 하네스를 발전시키며 다룬 설계 경험을 일반화한 기록이다. 모델명, 내부 평가 수치, 서비스별 세부 정책은 사용하지 않는다. 아래 경계는 하나의 설계 예시이며 제품의 기능·정책에 맞게 정해야 한다.

## 모든 요청이 같은 탐색을 필요로 하지는 않는다

- “블루투스 켜 줘”처럼 현재 기능 정보만으로 다음 실행을 결정할 수 있는 요청이 있다.
- 앞선 결과를 받아 여러 단계로 실행하더라도, 사용할 기능과 절차가 이미 명확할 수 있다.
- 반대로 한 문장의 요청이어도 새로운 capability 탐색이나 장기 실행 계획이 필요할 수 있다.

| 판단 기준 | Fast에 남길 수 있는 경우 | Deep을 검토할 경우 |
| --- | --- | --- |
| 기능 정보 | 필요한 capability가 제공됨 | 추가 탐색이 필요함 |
| 다음 행동 | 계약에 맞는 다음 실행이 명확함 | 여러 대안을 탐색·계획해야 함 |
| 후속 입력 | 지원하는 확인·선택 절차로 해결 | 새로운 의도 해석·계획이 필요함 |
| 자동화 | Fast의 계약에 명시된 범위 | 지속 상태·조건·스케줄 설계가 필요함 |
| 오류 복구 | 제공된 복구 절차로 해결 | 기능을 다시 찾거나 계획을 바꿔야 함 |

이 표의 핵심은 “짧은 요청은 Fast, 긴 요청은 Deep”으로 분류하지 않는 데 있다. 기준은 **현재 가진 정보와 실행 능력으로 요청을 처리할 수 있는가**다.

## 승격은 상태와 근거를 전달하는 경계다

![Fast 계층이 처리 가능성을 판단하고 추가 탐색이 필요한 요청만 근거와 문맥을 Deep 계층으로 전달하는 흐름](/data/images/posts/device-assistant-fast-deep/tier-routing.svg)

- Fast는 현재 capability로 처리할 수 있으면 도구를 호출하거나 결과를 안내한다.
- 범위를 벗어나면 무엇이 부족한지 설명하는 근거와 필요한 문맥을 넘긴다.
- Deep은 이전 결과를 이어받아 탐색·계획을 수행한다.
- 이미 실행한 행동을 다시 수행하지 않도록 실행 결과와 대기 상태를 보존한다.

초기에는 Fast의 완료·실패 상태를 구분해 후속 경로를 선택하는 구조를 도입했다. 이후에는 실패 여부만큼이나 **왜 추가 탐색이 필요한지**를 명확하게 만드는 일이 중요해졌다.

## 과도한 승격은 겹치는 지침에서 발생할 수 있다

적용 과정에서는 “불확실하면”, “여러 호출이 필요할 수 있으면”, “부수 효과가 있을 수 있으면” 같은 조건이 여러 지침에 중복됐다. 각각은 그럴듯하지만 함께 읽으면 대부분의 디바이스 요청이 승격 대상이 된다.

| 모호한 조건 | 문제 | 더 구체적인 판단 |
| --- | --- | --- |
| 여러 단계일 수 있다 | 단순 조회 후 실행까지 모두 승격 | 현재 capability와 절차로 끝낼 수 있는가? |
| 확신이 없다 | 일반적인 불확실성을 전부 Deep에 위임 | 어떤 정보가 부족하며 어디서 얻을 수 있는가? |
| 부수 효과가 있다 | 실행 정책과 추론 능력을 혼동 | 필요한 권한·확인 절차가 충족됐는가? |
| 관련 기능이 보인다 | 단어만 비슷한 기능에 억지로 라우팅 | 요청한 동작과 제약을 실제로 지원하는가? |

**Deep으로 보내는 것 자체가 안전장치는 아니다.** 민감한 실행의 권한·확인·정책 검증은 어느 계층에서 실행하든 지켜야 한다.

## 승격률만 낮추면 반대쪽 오류를 놓친다

| 평가 항목 | 확인할 질문 |
| --- | --- |
| 과도한 승격 | Fast가 처리할 수 있는 요청을 넘겼는가? |
| 필요한 승격 누락 | 정보가 부족한데 임의의 기능을 실행했는가? |
| 작업 성공 | 사용자가 원한 최종 상태에 도달했는가? |
| 응답 지연 | 사용자에게 첫 반응·완료까지 얼마나 걸렸는가? |
| 실행 비용 | 두 계층의 모델·도구 호출이 어떻게 늘었는가? |

- 같은 요청을 반복해 경계 판단의 변동을 확인한다.
- 성공 사례뿐 아니라 기능 미지원, 모호한 대상, 오류 복구, 조건부 요청을 포함한다.
- 과거 모델이 남긴 승격 결과를 그대로 정답으로 사용하지 않는다.
- “잘못 승격했다”와 “잘못 실행했다”의 비용이 다르므로 두 오류를 따로 기록한다.

아래 관계는 순차적으로 Fast를 먼저 실행하는 구조의 개념적 비용 모델이다. 실제 지연은 캐시·병렬 작업·도구 실행에 따라 달라진다.

```text
평균 처리 시간 ≈ Fast 처리 시간
               + 승격 확률 × (인계 비용 + Deep 추가 처리 시간)
```

Fast의 판단 비용을 지불한 뒤 Deep을 다시 실행하므로, 승격이 많은 요청군에서는 처음부터 Deep을 선택하는 편이 적절할 수도 있다.

## 프롬프트와 실행 환경을 함께 맞춘다

- Fast가 로드할 수 없는 Skill을 호출 후보처럼 보여 주지 않는다.
- 승격 정책과 도구 설명이 서로 다른 기준을 말하지 않도록 관리한다.
- 모델의 sampling·reasoning 설정을 기록해 지침 변경의 효과와 분리한다.
- 사용자에게 이미 안내한 내용과 실행한 작업을 인계해 중복 질문·중복 실행을 줄인다.

## 적용하면서 얻은 기준

**Fast·Deep의 경계는 모델 크기보다 실행 계약과 탐색 범위로 설명할 수 있어야 한다.**

- Fast가 처리할 수 있는 요청의 범위를 먼저 정의한다.
- 승격 사유는 실제 부족한 정보나 실행 능력을 가리키게 한다.
- 빠른 처리 비율과 최종 작업 성공률을 함께 본다.
- 제품의 capability가 바뀌면 기존 경계와 평가 정답도 다시 검토한다.

기능의 범위와 도구 경계를 나눴던 출발점은 [OpenClaw 컴포넌트 적용기](/posts/openclaw-component-application/)에서 다뤘다.
