**Fast는 제공된 도구와 정보로 다음 행동을 결정하고, Deep은 추가 기능 탐색과 계획이 필요한 요청을 이어받는다.** 처리 범위가 명확한 요청은 짧은 경로로 끝내고, 필요한 요청에만 탐색 비용을 쓰는 구조다.

## 어떤 요청을 어디서 처리하나

| 구분 | Fast에서 처리 | Deep으로 이어 처리 |
| --- | --- | --- |
| 사용 가능한 정보 | 필요한 도구와 입력값이 준비됨 | 필요한 기능을 더 찾거나 결과를 종합해야 함 |
| 다음 행동 | 제공된 절차 안에서 결정 가능 | 추가 탐색과 계획이 필요 |
| 예시 | 음량 조회 도구로 “현재 음량 알려줘” 처리 | 일정 조회·비교 기능을 찾아 “두 시간 비는 때 찾아줘” 처리 |
| 여러 단계인 경우 | 절차가 명확하면 Fast로 계속 진행 | 다음 행동을 정할 정보가 부족하면 Deep 검토 |

- **판단 기준은 현재 제공된 기능과 정보다.** 같은 일정 요청도 필요한 기능이 Fast에 이미 제공되어 있다면 Fast에서 처리할 수 있다.
- Fast·Deep은 실행 경로의 역할을 뜻한다. 모델 크기나 특정 제품 기능으로 고정되는 구분은 아니다.

![현재 정보로 처리할 수 있으면 Fast에서 진행하고 추가 탐색이 필요하면 문맥을 Deep으로 넘기는 구조](/data/images/posts/device-assistant-fast-deep/tier-routing.svg)

그림 1. 처리 가능한 요청은 Fast에 남기고, 부족한 정보가 있는 요청을 Deep으로 연결한다.

## 두 실행 경로를 메시지로 비교하기

**Fast에서 끝나는 경우에도 도구 호출과 결과 메시지가 오간다. Deep으로 넘길 때는 대화와 실행 결과를 함께 이어 준다.**

![왼쪽은 음량 조회를 Fast에서 완료하는 흐름, 오른쪽은 일정 탐색을 Deep으로 이어가는 흐름과 메시지 예시](/data/images/posts/device-assistant-fast-deep/tier-sequences.svg)

그림 2. 두 경로의 비교. 도구 이름·호출 ID·결과 값은 독립적으로 만든 설명용 예시다. 외부 도구는 서버가 실행하고, Deep 전환은 클라이언트의 후속 요청으로 진행하는 구성을 가정했다. 모델 호출·상태 저장·중간 스트리밍은 단순화했다.

- **Fast 완료:** `HumanMessage` → 도구 호출을 담은 `AIMessage` → 실행 결과인 `ToolMessage` → 답변을 담은 `AIMessage`로 이어진다.
- **Deep 전환:** Fast가 추가 탐색 필요를 알리면 첫 요청을 끝낸다. 클라이언트가 대화와 실행 상태를 포함해 다시 요청하고, 애플리케이션이 Deep을 선택한다. 사용자가 질문을 다시 입력하는 과정은 아니다.
- **요청과 결과 연결:** `ToolMessage.tool_call_id`는 대응하는 `AIMessage.tool_calls`의 `id`와 같아야 한다. 승격 안내와 경로 선택은 애플리케이션이 정하는 제어 정보다. [메시지 공식 문서](https://docs.langchain.com/oss/javascript/langchain/messages#tool-message)

## Deep에 무엇을 넘겨야 하나

| 넘길 정보 | 예시 | 필요한 이유 |
| --- | --- | --- |
| 사용자 요청과 조건 | “이번 주”, “두 시간 연속” | 원래 요구를 유지 |
| 확인된 정보와 도구 결과 | 이미 조회한 일정 | 불필요한 재조회와 중복 실행 방지 |
| 추가 탐색이 필요한 이유 | 현재 경로에 일정 조회 기능이 없음 | 다음 탐색의 출발점 제공 |
| 진행 상태 | 완료한 작업, 기다리는 입력, 선택된 경로 | 중단된 지점부터 이어 처리 |

- 호출 기록을 넘길 때는 **도구 호출과 대응하는 결과를 함께 유지**한다.
- 권한이나 사용자 확인이 필요한 작업은 어느 경로에서든 같은 실행 정책을 적용한다.

## 빠른 경로가 실제로 도움이 되는지 확인하기

**Fast에서 끝나는 비율과 최종 작업 성공을 함께 본다.**

- **불필요한 전환:** 현재 도구로 처리할 수 있는데 Deep으로 넘겼는가?
- **필요한 전환 누락:** 정보가 부족한데 추측으로 실행했는가?
- **지연과 비용:** 첫 반응·완료까지의 시간, 두 경로의 모델·도구 호출이 어떻게 달라졌는가?

순차적으로 Fast를 먼저 실행하면, Deep으로 넘어간 요청에는 Fast의 판단 시간과 인계 비용도 더해진다. 대부분이 Deep으로 넘어가는 요청군은 처음부터 Deep을 선택하는 구성도 비교할 수 있다.
