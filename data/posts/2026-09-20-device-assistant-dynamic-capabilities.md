**Skill에 좋은 레시피와 행동 지침을 적어도, 모델이 그 Skill을 선택해 읽지 않으면 지침은 실행에 영향을 주지 못한다.** 하위 에이전트의 기능을 Skill로 표현하면서 먼저 부딪힌 것은 본문의 품질보다 어떤 Skill을 읽을지 결정하는 문제였다.

초기에는 하위 에이전트별 기능 설명과 호출 절차를 각각 Skill로 구성했다. 이후 기능 간 경계가 겹치는 요청에서 선택이 흔들리는 문제를 다루기 위해, **요청에 맞는 capability를 탐색하고 모델과 하네스에 동적으로 노출하는 별도 계층**을 적용했다.

이 글은 그 구조 변경의 문제의식과 책임 분리를 설명한다. 사례와 도표는 공개 가능한 수준으로 일반화했으며, 내부 모듈명과 프로토콜 대신 역할과 정보 흐름을 사용한다.

## Skill을 읽는 것 자체가 모델의 결정이었다

초기 흐름은 사용자 요청을 보고 관련 Skill을 고른 뒤, 해당 본문을 읽고 레시피와 행동 지침을 따르는 방식이었다. 여기서 Skill은 하위 에이전트의 실행 코드 자체가 아니라 **기능의 사용 조건과 호출 방법을 설명하는 지침**이었다.

![요청을 받은 모델이 Skill 선택을 먼저 해야 상세 레시피와 행동 지침을 읽고 실행할 수 있는 초기 흐름](/data/images/posts/device-assistant-dynamic-capabilities/skill-selection-bottleneck.svg)

- **첫 번째 판단:** 이 요청에 어떤 Skill을 읽어야 하는가?
- **본문을 읽은 뒤의 판단:** 지원 범위가 맞는가, 어떤 순서로 기능을 호출해야 하는가?
- 두 판단은 별개다. 상세한 레시피가 두 번째 판단을 돕더라도 첫 번째 선택이 틀리면 활용되지 않는다.
- 이름과 짧은 설명만으로 경계를 구분하기 어려울수록, 본문을 읽기 전에 필요한 판단이 커진다.

예를 들어 어떤 Skill의 본문에 “이 기능을 쓰기 전에 다른 기능으로 대상을 찾아야 한다”는 규칙이 있어도, 그 Skill을 읽지 않으면 모델은 해당 선행 조건을 알 수 없다.

## 하위 에이전트의 경계는 사용자 요청의 경계와 달랐다

디바이스 기능을 에이전트별로 나누는 기준과 사용자가 표현하는 목표는 일대일로 대응하지 않았다. 하나의 요청이 조회·선택·수정을 함께 포함하기도 하고, 비슷한 설명을 가진 기능이 서로 다른 범위의 작업을 담당하기도 했다.

| 설명용 요청 | 겹쳐 보이는 기능 | 이름만으로 판단하기 어려운 부분 |
| --- | --- | --- |
| 내일 회의를 찾아서 오후 3시로 옮겨 줘 | 검색·일정 조회·일정 수정 | 어떤 조회 결과를 어떤 수정 기능에 넘길 것인가? |
| 아까 찾은 사람에게 메시지 보내 줘 | 대상 검색·연락처·메시지 | 이전 결과를 재사용할 수 있는가, 새 조회가 필요한가? |
| 배터리를 오래 쓰도록 설정해 줘 | 기기 설정·최적화·사용법 안내 | 설명을 제공할 기능과 상태를 바꿀 기능 중 무엇이 필요한가? |

위 예시는 경계 문제를 설명하기 위한 가상 요청이다. 실제 담당 기능과 선행 조건은 해당 실행 환경의 capability 계약에 따라 달라진다.

이 구조에서 관찰한 문제는 **첫 선택이 뒤의 행동까지 제약한다는 점**이었다.

- 잘못 선택한 Skill 안에서 요청을 해석하면, 그 범위에 맞춰 요청을 좁히거나 맞지 않는 절차를 따를 수 있다.
- 관련 Skill을 놓치면 필요한 레시피나 행동 규칙도 함께 빠진다.
- 선택 규칙을 전역 프롬프트에 계속 추가하면 Skill 본문의 설명과 중복되거나 서로 어긋날 수 있다.
- 모든 Skill을 읽게 하면 선택에 필요한 정보는 늘지만, 불필요한 본문과 겹치는 규칙도 함께 늘어난다.

## 에이전트 이름을 고르기 전에 실행 가능한 기능을 드러냈다

이를 해결하기 위해 요청과 현재 문맥에 맞는 기능 정보를 제공하는 **capability 탐색 계층**을 하네스에 연결했다. 여기서 capability는 “어떤 에이전트인가”를 넘어, **어떤 행동을 지원하며 어떤 제약과 실행 수단을 갖는가**를 표현한다.

![요청과 문맥에서 capability를 탐색하고 같은 결과를 모델의 판단 정보와 하네스의 실행 구성으로 나누어 반영하는 구조](/data/images/posts/device-assistant-dynamic-capabilities/dynamic-capability-exposure.svg)

- 하네스가 요청과 문맥을 바탕으로 관련 capability를 먼저 탐색한다.
- 모델에는 관련 기능의 설명, 지원 범위, Skill 후보 등 현재 판단에 필요한 정보를 보여 준다.
- 하네스에는 발견한 기능을 분류하고 프롬프트·도구 구성에 반영할 구조화된 정보를 전달한다.
- 상세 절차가 필요한 Skill은 본문을 추가로 로드하고, 정보가 부족하면 후속 탐색을 수행한다.
- 실행 결과를 받은 뒤 다음 단계에 필요한 정보와 기능을 다시 판단한다.

**Skill 선택의 출발점을 전체 에이전트 목록에서 요청별 기능 후보로 바꾼 것**이다. 모델이 선택을 전혀 하지 않게 된 것은 아니다. 선택에 앞서 읽을 수 있는 근거와 실제 실행 환경을 정렬하도록 구조를 바꿨다.

## 모델에 보여 주는 정보와 하네스가 사용하는 정보를 함께 맞춘다

동적 노출을 프롬프트에 설명 문장을 추가하는 것으로만 구현하면, 모델이 읽은 기능과 실제 호출 가능한 도구가 어긋날 수 있다. 탐색 결과는 두 소비자가 각자의 역할에 맞게 사용할 수 있어야 했다.

| 소비자 | 필요한 정보 | 맡는 책임 |
| --- | --- | --- |
| 모델 | 기능 설명·제약·Skill 후보·로드된 절차 | 사용자 목표에 맞는 다음 행동 판단 |
| 하네스 | 기능 종류·식별 정보·연결할 도구 정의 | 결과 분류, 프롬프트 구성, 필요한 도구 연결 |
| 실행 계층 | 유효한 입력·실행 대상·권한·현재 상태 | 실제 동작 수행과 결과 반환 |

- 같은 탐색 결과라도 모델용 설명과 하네스용 구조화 데이터의 표현은 다를 수 있다.
- 기능 설명이 프롬프트에 나타나는 경로와 호출 도구가 준비되는 경로를 함께 점검한다.
- 하나의 capability가 반드시 하나의 도구에 대응하지는 않는다. 공통 실행 도구를 공유하거나 여러 단계의 절차를 제공할 수도 있다.
- 탐색됐다는 이유만으로 실행을 허용하지 않는다. 권한과 입력 유효성은 실행 계약에 따라 확인한다.

아래는 책임 경계를 나타내는 의사 코드다. 실제 구현의 함수나 데이터 스키마를 옮긴 코드는 아니다.

```text
capabilities = discover(request, context)

model_context = describe_candidates(capabilities)
runtime_tools = prepare_tools(capabilities, runtime_policy)

decision = model.decide(model_context, runtime_tools)

if decision.needs_instructions:
    load_selected_skill_details()
elif decision.needs_more_capabilities:
    discover_for_next_step()
else:
    validate_and_execute(decision)
```

## 탐색 계층과 Skill의 책임을 나눴다

Skill은 여전히 기능별 레시피와 행동 지침을 제공한다. 바뀐 부분은 그 Skill과 실행 기능에 도달하기까지의 정보 제공 방식이다.

| 기준 | 하위 에이전트별 Skill 선택에 의존 | 동적 capability 탐색을 적용 |
| --- | --- | --- |
| 첫 판단의 근거 | 이름·설명으로 읽을 Skill 선택 | 요청·문맥에 맞는 기능 후보를 보고 선택 |
| 경계가 겹치는 요청 | 먼저 고른 Skill 안에서 해석하기 쉬움 | 후보의 실제 행동·제약을 비교할 근거 제공 |
| 레시피와 행동 지침 | 선택한 Skill 본문에서 로드 | 필요한 Skill 본문을 상세 로드해 사용 |
| 모델과 실행 환경 | 설명과 도구 구성을 별도로 관리하기 쉬움 | 탐색 결과를 양쪽 구성에 반영 |
| 실패 조사 | 모델이 왜 그 Skill을 골랐는지에 집중 | 탐색·전달·로드·판단·실행으로 나눠 조사 |

이 구조의 장점은 선택 문제를 하나의 긴 프롬프트 안에 모두 넣지 않아도 된다는 점이다. 대신 탐색 결과의 품질과, 그 결과를 실제 모델 입력·도구 구성으로 옮기는 경계가 새로운 검증 대상이 된다.

## 실패를 단계별로 확인할 수 있게 한다

capability를 동적으로 노출해도 관련 기능이 누락되거나 잘못된 정보가 전달되면 라우팅은 실패한다. 따라서 개선 여부를 확인할 때는 다음 질문을 분리해야 한다.

| 단계 | 확인할 질문 |
| --- | --- |
| 탐색 | 요청한 행동을 처리할 기능이 후보에 포함됐는가? |
| 전달 | 후보가 분류·병합·필터링 과정에서 누락되지 않았는가? |
| 상세 로드 | 필요한 레시피와 제외 조건이 모델에게 보였는가? |
| 판단 | 도메인 단어의 유사성보다 실제 지원 행동을 기준으로 골랐는가? |
| 실행 | 모델이 선택한 기능을 하네스가 실제로 연결할 수 있었는가? |
| 결과 | 사용자의 목표를 달성했고 요청하지 않은 행동을 추가하지 않았는가? |

- 경계가 겹치는 요청과 여러 기능을 이어야 하는 요청을 평가에 포함한다.
- 정답 capability가 후보에 없는 실패와, 후보에 있는데도 잘못 고른 실패를 구분한다.
- 후보가 없거나 부족할 때 추가 탐색·질문·미지원 안내 중 적절한 행동을 하는지 확인한다.
- 같은 작업을 이어 갈 때는 발견한 정보와 실행 상태를 유지하되, 새 요청에 무관한 후보를 계속 남기지 않도록 수명을 관리한다.
- 탐색 지연과 추가 호출 비용도 작업 성공률과 함께 본다.

## 적용하면서 얻은 교훈

**레시피를 잘 작성하는 문제와, 그 레시피를 읽어야 하는 시점을 찾아 주는 문제는 서로 다른 설계 과제였다.**

- 하위 에이전트의 경계가 사용자 의도와 항상 일치한다고 가정하지 않는다.
- Skill은 상세 절차와 행동 지침을 관리하는 단위로 유지한다.
- capability 탐색은 현재 요청에서 판단할 후보와 근거를 드러내는 역할을 맡긴다.
- 하네스는 그 정보를 실제 모델 입력과 실행 구성에 일관되게 반영한다.
- 모델은 드러난 기능을 바탕으로 선택·계획하고, 부족한 정보는 추가로 확보한다.

기능 설명, 도구 실행, 세션의 책임을 처음 나눴던 과정은 [OpenClaw 컴포넌트 적용기](/posts/openclaw-component-application/)에 정리했다.
