**디바이스 어시스턴트의 최종 문장만 보면, 요청을 실제로 실행했는지와 그럴듯하게 설명했는지를 구분하기 어렵다.** 도구 호출을 기록하는 데서 시작해 실행 과정을 재현하고 평가하는 구조로 확장한 이유다.

이 글은 디바이스 어시스턴트의 로깅·평가 경험을 후속 하네스 설계와 연결한다. 예시는 공개 설명을 위해 구성했으며 실제 사용자 기록이나 내부 평가 수치는 포함하지 않는다.

## 로그에서 찾으려던 것은 실패한 판단의 위치였다

예를 들어 “주방 불 꺼 줘”라는 요청에 “껐습니다”라고 답했다면, 확인할 질문은 문장의 자연스러움보다 많다.

- 관련 capability가 검색됐는가?
- 모델에게 올바른 기능 설명이 전달됐는가?
- 호출 대상과 인자가 요청에 맞았는가?
- 외부 기능이 성공했는가, 실패했는데 성공으로 설명했는가?
- 같은 작업을 중복 실행하거나 무관한 작업을 추가하지 않았는가?

| 관측 범위 | 알 수 있는 것 | 여전히 부족한 것 |
| --- | --- | --- |
| 최종 응답 | 사용자가 받은 설명 | 실제 도구 실행과 판단 경로 |
| 도구 호출 로그 | 도구·인자·결과·지연 | 앞선 탐색과 요청 전체 문맥 |
| 연결된 trace | 모델·탐색·도구 호출의 관계 | 고정된 재현 환경과 성공 기준 |
| 실행 가능한 평가 사례 | 특정 조건에서 행동을 비교 | 실제 환경 전체에 대한 일반화 |

## 관측과 평가를 연결하되 같은 것으로 취급하지 않는다

![요청과 실행 기록에서 평가 후보를 만들고 컨텍스트·성공 조건을 고정한 뒤 회귀 평가로 연결하는 구조](/data/images/posts/device-assistant-trace-evaluation/trace-evaluation.svg)

- OpenClaw 실험에서는 도구 이름, 인자, 결과, 지연 시간과 세션 기록을 관측했다.
- 후속 하네스에서는 내부 도구 호출까지 추적하고, 모델·도구·응답 생성 흐름을 trace로 연결했다.
- 대화 메시지만으로 재현되지 않는 요청을 다루면서 기기·사용자 컨텍스트도 기록 범위에 포함했다.
- 모델 행동 평가와 런타임 단위 테스트의 목적을 구분해 평가 실행·데이터 관리의 책임을 분리했다.

[Langfuse의 데이터 모델](https://langfuse.com/docs/observability/data-model)은 요청 흐름 안의 관측을 연결하는 개념을 제공한다. 다만 trace가 존재한다는 사실만으로 그것이 곧 재현 가능한 테스트가 되지는 않는다.

## 대화가 같아도 실행 조건이 다르면 결과는 달라진다

“거기 불 꺼 줘”를 다시 실행할 때, 당시 화면이나 선택된 기기가 빠져 있으면 원래 요청과 다른 문제를 풀게 된다.

| 재현 조건 | 고정하거나 기록할 정보 | 빠졌을 때의 혼동 |
| --- | --- | --- |
| 사용자 의도 | 발화와 필요한 대화 이력 | 지시 대상·후속 답변을 다르게 해석 |
| 기기 문맥 | 관련 기기·화면·기능 상태 | 다른 대상이나 미지원 기능을 선택 |
| 시간·지역 | 기준 시각·시간대·언어 | “내일”, 시간, 지역 질의를 다르게 해석 |
| 실행 정의 | 모델·지침·Skill·도구 버전 | 어떤 변경이 결과를 바꿨는지 불명확 |
| 외부 관측 | 고정 응답 또는 실행 환경 | 과거 상태와 현재 상태의 차이를 모델 오류로 해석 |

- 컨텍스트를 기록할 때는 재현에 필요한 필드만 선별한다.
- 식별자와 개인 정보는 평가 목적에 맞게 제거하거나 일관된 가상 값으로 대체한다.
- seed나 sampling 설정을 고정해도 외부 상태와 모델 서비스의 변화까지 사라지는 것은 아니다.
- 기록한 컨텍스트가 완전하지 않으면 어떤 조건을 재현하지 못했는지 남긴다.

## 행동별 성공 기준을 나눈다

OpenClaw에서 평가 도구를 구성할 때 함수 실행, 도구 호출, Skill 조회, 실행 순서, 지연 시간, 멀티턴 문맥을 별도로 확인했다. 후속 평가에서도 이 분리는 유효했다.

| 평가 축 | 예시 | 적합한 검증 방식 |
| --- | --- | --- |
| 도구 선택·인자 | 요청한 기기와 동작을 전달 | 규칙·스키마 기반 검사 |
| 실행 결과 | 최종 기기 상태가 요청과 일치 | 상태 기반 검사 |
| 행동 제약 | 확인 전 전송 금지, 취소 후 실행 금지 | 이벤트 순서·금지 행동 검사 |
| 사용자 설명 | 실제 결과를 왜곡하지 않음 | 규칙 + 필요한 경우 모델 평가 |
| 효율 | 불필요한 탐색·호출이 늘지 않음 | 지연·호출 수·토큰 비교 |

**하나의 기록된 실행 경로가 유일한 정답은 아니다.** 같은 목표를 만족하는 다른 유효 경로가 있다면 허용하고, 꼭 필요한 선행 관계나 금지 행동만 강하게 제한한다.

## Trace를 평가 데이터로 승격하는 절차

1. **선별:** 실패나 드문 경로에서 재현할 가치가 있는 사례를 선택한다.
2. **정제:** 불필요한 이력·개인 정보·환경 종속 값을 제거한다.
3. **조건 고정:** 초기 상태, 필요한 컨텍스트, 외부 관측의 제공 방식을 정한다.
4. **성공 기준 작성:** 기대 상태와 금지 행동을 사람이 검토한다.
5. **버전 기록:** 데이터·평가기·지침·모델 설정을 함께 추적한다.
6. **비교 실행:** 변경 전후를 실행하고 실패 경로를 다시 trace로 조사한다.

[Langfuse의 dataset 기능](https://langfuse.com/docs/evaluation/experiments/datasets)은 입력과 기대 결과를 관리하고 실험에 사용하는 기반을 제공한다. 어떤 trace를 선택할지, 무엇을 정답으로 볼지는 별도로 결정해야 한다.

## Replay와 실제 행동 평가는 구분한다

- **Replay:** 기록된 도구 결과를 다시 제공해 이후 판단을 비교한다. 실제 기기를 조작할 필요는 없지만 새로운 행동의 효과를 평가하는 범위는 제한된다.
- **상태 기반 실행:** 초기 상태를 고정한 테스트 환경에서 도구가 상태를 바꾸게 한다. 최종 상태를 확인할 수 있지만 환경 구현과 초기화가 필요하다.
- **멀티턴 평가:** 확인·선택에 대한 사용자 응답까지 포함한다. 어떤 응답을 제공하는지와 종료 조건을 함께 정의해야 한다.

실제 기기를 대상으로 평가할 때는 테스트 계정·대상·실행 범위를 별도로 통제해야 한다. 재현을 위해 운영 요청을 그대로 다시 보내는 방식은 평가 환경과 실제 사용 환경을 섞는다.

## 적용하면서 얻은 기준

**관측은 무슨 일이 일어났는지 설명하고, 평가는 어떤 조건에서 무엇이 성공인지 명시한다.** 둘을 연결하되 책임을 구분해야 했다.

- 요청 전체를 재현할 수 있는 최소 컨텍스트를 기록한다.
- 도구 선택, 최종 상태, 사용자 설명을 서로 다른 축으로 검증한다.
- 과거 모델의 행동을 검토 없이 정답으로 사용하지 않는다.
- 단위 테스트는 실행 계약을, 행동 평가는 모델과 환경이 결합한 결과를 확인하게 한다.

평가 데이터의 선별·정제 과정을 더 자세히 다룬 글은 [Trace에서 평가 데이터로](/posts/trace-to-eval-data-flywheel/), 실행 조건의 재현 문제는 [재현 가능한 에이전트 평가](/posts/reproducible-agent-evaluation/)에서 이어 볼 수 있다.
