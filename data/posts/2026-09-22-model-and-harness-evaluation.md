*그림 1. 평가 대상은 모델과 실행 하네스의 조합이다. 평가를 진행하는 쪽은 조건을 준비하고, 이 조합이 도구·환경과 상호작용한 과정과 결과를 채점한다.*

**에이전트를 평가할 때는 모델이 올바른 행동을 제안했는지와 함께, 하네스가 그 행동을 실행하고 결과를 다음 판단에 정확히 연결했는지 확인해야 한다.** 같은 모델이라도 제공받는 도구, 전달되는 실행 결과, 상태 유지와 중단 규칙에 따라 결과가 달라질 수 있다.

- **모델의 역할:** 주어진 문맥에서 답변이나 도구 호출을 생성.
- **실행 하네스의 역할:** 모델 입력을 구성하고, 도구 실행·결과 전달·상태 유지·재호출을 조율.
- **함께 평가할 것:** 사용자의 목표 달성, 지켜야 할 실행 조건, 종료 이유와 소모한 자원.
- **예시:** “10분 타이머 하나 만들어 줘”에서 생성 함수를 맞히는 것뿐 아니라, 중복 없이 생성하고 실제 결과에 맞게 응답하는지 확인.

이 글의 타이머 사례는 평가 범위를 설명하기 위한 가상 예시다. 그림을 누르면 확대할 수 있고, `100%` 보기에서는 본문과 같은 크기로 글자를 읽을 수 있다.

## 실행 하네스와 평가 하네스는 역할이 다르다

**하네스(harness)는 실행을 묶어 조율하는 주변 소프트웨어를 뜻한다.** 무엇을 실행하느냐에 따라 역할을 구분해야 한다.

| 구분 | 조율하는 대상 | 책임의 예 |
| --- | --- | --- |
| 실행 하네스(Agent harness) | 사용자의 작업을 수행하는 에이전트 | 입력 구성, 도구 노출과 실행 연결, 대화·작업 상태 유지, 재호출과 중단 |
| 평가 하네스(Evaluation harness) | 평가 사례의 반복 실행 | 초기 조건 준비, 평가 대상 호출, 실행 기록 수집, 시간 제한, 채점과 집계 |
| 도구·환경 | 행동이 적용되는 대상 | 타이머 생성, 저장된 상태 변경, 성공·오류 결과 반환 |
| 채점기(Grader) | 실행에서 얻은 증거 | 기대 행동, 필수 조건, 최종 상태를 기준으로 판정 |

- **평가 대상:** 모델과 실행 하네스의 조합. 실행 하네스의 변경도 에이전트 행동을 바꿀 수 있음.
- **평가 장치:** 평가 하네스와 채점기. 연결 과정에서 입력이나 도구 결과를 바꾸면 평가 자체가 왜곡될 수 있음.
- **구현 경계:** 두 역할이 하나의 프로그램 안에 있을 수도 있음. 같은 이름을 쓰는지보다 어느 쪽이 어떤 결정을 하는지 구분.
- **도구 연결:** 실행 하네스가 직접 도구를 실행할 수도 있고, 외부 실행자에게 요청을 넘기고 결과를 돌려받을 수도 있음. 평가에서는 실제 연결 경계를 확인해야 함.

모델에 오류를 다시 판단하게 하는 것은 실행 하네스의 정책일 수 있다. 반면 평가 장치가 실패한 사례를 몰래 새로 시작하는 것은 별도의 평가 정책이다. **누가 재시도를 결정했는지 남겨야 실행 품질과 평가 조건을 구분할 수 있다.**

## 출력 비교에서 실행 조합의 검증으로

**평가 대상에 하네스를 포함하면, 한 번의 예측뿐 아니라 그 예측이 실행 과정에서 어떻게 사용되는지도 확인한다.**

| 비교 기준 | 고정 입력에서의 판단 평가 | 모델과 실행 하네스를 함께 보는 평가 |
| --- | --- | --- |
| 질문 | 이 문맥에서 다음 출력이 맞는가? | 실제로 전달받은 결과를 활용해 작업을 수행하는가? |
| 입력 구성 | 평가 사례에서 준비한 문맥 | 실행 중 하네스가 구성하는 문맥과 도구 정보 |
| 도구 결과 | 고정된 결과를 입력에 포함할 수 있음 | 실제 호출에 대응한 결과의 전달까지 관찰 |
| 상태 | 평가 사례로 제공한 상태 | 행동에 따른 변화와 다음 호출에서의 복원 |
| 실행 범위 | 분리한 판단 또는 정해진 재생 구간 | 여러 모델 호출·도구 실행·재시도로 이어지는 작업 |
| 주요 증거 | 입력·예측·기대 결과 | 실제 입력, 호출·결과 기록, 상태, 종료 이유 |

- **도구 검색:** 필요한 도구가 후보에 없으면 모델이 올바른 호출을 선택하기 어려움. 검색 결과와 모델에 실제 노출된 도구를 함께 확인.
- **입력 구성:** 같은 사용자 요청이라도 이전 결과가 누락되거나 오래된 상태가 전달되면 다른 판단으로 이어질 수 있음.
- **실행 수명:** 한 번의 모델 응답이 도구 호출일 수 있고, 한 사용자 요청에 여러 모델 호출이 필요할 수 있음.
- **평가 범위와 방식의 구분:** 하네스를 포함해도 고정된 도구 결과를 주는 재생 평가를 할 수 있음. 하네스를 호출했다는 사실만으로 실제 환경의 최종 상태까지 검증한 것은 아님.

[고정 프롬프트 기반 평가](/posts/fixed-prompt-plan-evaluation/)는 특정 판단을 분리하는 데 유용하다. 전체 실행을 평가할 때는 그 판단을 둘러싼 입력 구성과 실행 연결까지 함께 보게 된다.

## 하나의 요청이 여러 번의 판단으로 이어진다

![초기 환경 준비부터 모델과 하네스의 도구 실행 반복, 기록과 최종 상태의 채점까지 이어지는 시퀀스](/data/images/posts/model-and-harness-evaluation/interaction-sequence.svg)

*그림 2. 하나의 도구 호출을 포함한 실행 예시. 더 많은 행동이 필요하면 모델 판단 → 도구 실행 → 결과 전달을 반복한다. 도구 환경은 실제 서비스의 격리된 환경이나 상태를 재현하는 시뮬레이터일 수 있다.*

1. **조건 준비:** 평가 사례의 초기 상태와 목표, 시간·호출 제한을 설정.
2. **실행 시작:** 요청을 실행 하네스에 전달. 하네스는 문맥과 사용 가능한 도구를 모델 입력으로 구성.
3. **행동 제안:** 모델이 도구와 인자를 선택.
4. **실행 연결:** 하네스가 도구 호출을 실행 경계로 전달하고 해당 호출의 결과를 수집.
5. **후속 판단:** 실제 결과와 필요한 상태를 다음 모델 입력에 반영.
6. **종료와 판정:** 완료·오류·제한 도달 등 종료 이유를 기록하고, 실행 과정과 환경의 최종 상태를 채점.

- **결과의 연결:** 도구 호출과 반환 결과가 정확히 대응하는지, 다른 호출의 결과가 섞이지 않는지 확인.
- **상태의 수명:** 대화 이력과 작업 상태가 이어지더라도 환경의 실제 상태와 일치하는지 별도로 확인.
- **완료의 의미:** API 응답을 받았다는 것, 모델이 완료라고 말했다는 것, 사용자의 목표 상태에 도달했다는 것은 각각 다른 사실.
- **평가 장치의 중단:** 평가 제한에 도달해 멈췄다면 그 이유를 남김. 에이전트가 스스로 정상 종료한 것과 구분.

## 같은 실패처럼 보여도 원인은 다를 수 있다

**최종 답변이 틀렸다는 사실만으로 모델의 판단이 원인이라고 단정할 수 없다.** 먼저 실행 경계별 증거를 대조해야 한다.

| 관찰한 현상 | 먼저 대조할 증거 | 확인할 가능성 |
| --- | --- | --- |
| 엉뚱한 도구를 선택함 | 도구 후보, 모델에 전달한 명세, 실제 모델 출력 | 필요한 도구가 빠졌는지, 후보가 있어도 선택을 잘못했는지 |
| 올바른 도구를 골랐는데 인자가 바뀜 | 모델이 생성한 인자와 실행자에게 전달된 인자 | 입력 변환이나 실행 연결에서 값이 달라졌는지 |
| 성공한 작업을 다시 수행함 | 호출 횟수, 각 호출의 결과, 다음 모델 입력 | 결과 누락·상태 복원 실패·모델의 중복 판단·하네스의 자동 재시도 여부 |
| 완료라고 답했지만 상태가 그대로임 | 도구 실행 기록과 별도로 조회한 환경 상태 | 호출이 실행되지 않았는지, 실행 실패를 놓쳤는지, 응답이 잘못됐는지 |
| 평가가 끝나지 않음 | 모델 호출·도구 대기 시간, 반복 행동, 종료 기록 | 도구 지연, 반복 판단, 중단 규칙 누락, 평가 장치 오류 여부 |

### 타이머가 두 개 생긴 경우

- **모델 판단의 문제 가능성:** 첫 생성의 성공 결과를 실제로 받았는데도 모델이 생성 호출을 다시 제안.
- **하네스 연결의 문제 가능성:** 도구는 성공했지만 결과가 다음 입력에서 누락되거나 잘못 대응되어 모델이 작업 상태를 알지 못함.
- **재시도 정책의 문제 가능성:** 응답이 유실된 상황에서 하네스가 같은 생성 요청을 자동으로 다시 전송.
- **환경의 영향 가능성:** 같은 요청이 반복될 때 중복 생성을 막는지 여부는 도구의 동작 규칙에 달려 있음.

**실행 기록은 원인을 좁히는 증거이며, 원인을 확정하는 실험과는 다르다.** 의심한 경계의 입력·응답·정책을 통제한 뒤 재현해야 한다. 모델과 하네스, 환경의 문제가 함께 나타날 수도 있다.

## 무엇을 성공으로 볼지 나누어 정의한다

**최종 상태와 실행 중 지켜야 할 조건을 함께 정의하고, 서로 다른 실패를 한 점수로 섞지 않는다.**

| 판정 축 | 타이머 예시 | 필요한 증거 |
| --- | --- | --- |
| 판단의 정확성 | 올바른 생성 도구와 지속시간을 선택 | 실제 모델 입력과 출력 |
| 실행 연결의 정확성 | 호출과 결과가 대응하고 다음 판단에 반영됨 | 전달 전후 인자, 도구 결과, 후속 입력 |
| 작업의 성공 | 활성 타이머가 정확히 하나이며 지속시간이 맞음 | 초기 상태와 최종 환경 상태 |
| 과정의 제약 | 금지된 변경 없이 정해진 재시도 조건을 지킴 | 전체 호출 이력과 상태 변화 |
| 자원 사용 | 시간·모델 호출·도구 호출이 허용 범위 안에 있음 | 소요 시간, 호출 횟수, 설정한 제한 |

- **상태를 직접 확인:** “생성 완료”라는 응답만으로 완료를 판정하지 않고, 해당 작업의 실제 상태를 읽을 수 있는 관측 수단을 준비.
- **경로의 유연성:** 같은 목표에 도달하는 여러 경로를 허용하되, 반드시 지켜야 할 중간 조건은 별도로 검사.
- **실패의 분리:** 목표 미달, 제약 위반, 실행 제한 도달, 도구 환경 오류, 평가 장치 오류를 구분해 기록.
- **보고할 모수:** 실행한 사례 수와 반복 횟수, 정상 판정·오류·미완료 수를 함께 제시. 제외 규칙과 재실행 횟수도 남겨 유리한 결과만 선택하지 않음.

일부 도구를 고정된 응답으로 대신했다면 검증한 것은 그 응답 아래의 동작이다. 실제 상태를 변경하지 않은 실행에서 상태 기반 성공률을 보고해서는 안 된다.

## 비교 실험에서 무엇을 고정해야 할까

**모델과 하네스를 함께 평가하더라도, 무엇의 영향을 비교하는지는 먼저 정해야 한다.**

| 비교 목적 | 바꿀 대상 | 유지하거나 차이를 기록할 조건 |
| --- | --- | --- |
| 모델 변경의 영향 | 모델 | 하네스, 도구 명세, 평가 사례, 초기 환경과 판정 기준 |
| 하네스 변경의 영향 | 입력 구성·결과 전달·상태 유지 등의 정책 | 모델, 평가 사례, 도구 환경과 판정 기준 |
| 제품 조합의 품질 | 모델과 하네스의 조합 | 동일한 작업 목표와 환경 조건. 차이가 한 요소의 효과라고 단정하지 않음 |

- **경계 검사:** 고정된 입력과 도구 결과로 결과 전달, 상태 복원, 중단 규칙 같은 좁은 조건을 확인.
- **상호작용 검사:** 실제 행동에 반응하는 도구 환경에서 다음 판단이 이어지게 하고 목표와 부작용을 확인.
- **환경 격리:** 실행마다 초기 상태를 복원해 앞선 사례가 다음 사례의 결과를 바꾸지 않게 함.
- **재현 정보:** 모델·하네스·평가 사례·도구 환경·채점 기준의 버전, 초기 상태, 실행 제한과 반복 횟수를 기록.
- **변동성:** 같은 조건에서도 실행 경로가 달라질 수 있으므로 반복 결과의 분포와 실패 유형을 확인. 환경의 난수나 시간을 통제해도 모델까지 완전히 결정적으로 동작한다고 가정하지 않음.

평가 대상이 넓어질수록 모든 실패를 한 번에 설명하려 하기보다 **좁은 경계 검사로 원인을 분리하고, 상호작용 평가로 전체 작업의 결과를 확인하는 구성**이 유용하다.

## 설명 범위와 함께 읽을 글

- **설명 범위:** 로컬 소스와 이력에서 확인한 실행·평가의 책임을 역할 중심으로 재구성한 설명. 특정 구현의 필수 규격을 제시하는 글은 아님.
- **예시의 범위:** 사례와 다이어그램은 독립적으로 구성한 설명용 예시. 모델·업무 서비스를 실행해 성능을 측정하거나 특정 평가 체계의 구현 완료를 주장하지 않음.
