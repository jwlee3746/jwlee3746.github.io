**“응”이나 “첫 번째”는 짧은 발화지만, 실행 관점에서는 이전 요청을 가리키는 중요한 입력이다.** 디바이스 어시스턴트가 이 답변을 새 요청으로 처리하면 대화는 자연스러워 보여도 실제 작업은 이어지지 않는다.

이 글은 [OpenClaw 컴포넌트 적용기](/posts/openclaw-component-application/)에서 다룬 후속 대화 연결 경험을 확장한다. 아래 메시지·상태 이름은 공개 설명을 위한 예시이며 실제 서비스 프로토콜이 아니다.

## 대화 기록과 실행의 연속성은 다르다

메시지를 보내려는데 동명이인이 검색됐다고 가정하자. 사용자는 “첫 번째”라고 답한다. 대화 기록에는 후보가 있지만, 외부 실행 서비스에는 어떤 대기 중 요청의 후보를 골랐는지 알려 줘야 한다.

| 구분 | 보존할 정보 | 보존하지 않았을 때 |
| --- | --- | --- |
| 대화 세션 | 사용자·대화 기록·앞선 설명 | 답변의 언어적 맥락을 잃음 |
| 실행 참조 | 이어 갈 작업의 식별자 | 새 작업으로 시작하거나 잘못된 작업을 재개 |
| 대기 상태 | 확인·선택·값 입력 중 무엇을 기다리는가 | 같은 “응”을 다른 의미로 해석 |
| 질문 당시 후보 | 사용자에게 실제로 보여 준 목록 | 재검색 순서가 바뀌어 다른 대상을 선택 |

**세션에 기록이 남아 있다는 사실만으로 외부 실행의 재개가 보장되지는 않는다.**

## 질문을 실행 결과의 일부로 다룬다

![외부 기능이 선택을 요청하고 사용자의 후속 답변이 이전 실행 참조와 함께 전달되어 작업을 완료하는 시퀀스](/data/images/posts/device-assistant-hitl/continuation-sequence.svg)

- 첫 도구 호출에서 완료 결과 대신 사용자 입력 요청이 돌아올 수 있다.
- 하네스는 대기 중인 실행 참조와 필요한 입력의 종류를 보존한다.
- 어시스턴트는 도구가 요구한 질문을 사용자에게 전달한다.
- 후속 답변은 원래 요청, 선택한 값, 이전 실행 참조와 함께 전달한다.
- 외부 기능이 완료를 확인한 뒤 성공을 안내한다.

적용 과정에서는 도구 결과에 포함된 확인·선택 정보를 모델에게 전달하고, 후속 호출에 이전 요청 참조를 명시적으로 실어 보내는 방식으로 연결을 보완했다.

## 확인·선택·누락값 입력을 같은 질문으로 처리하지 않는다

| 입력 요청 | 사용자에게 필요한 응답 | 지켜야 할 조건 |
| --- | --- | --- |
| 확인 | 진행·취소 의사 | 모델이 사용자의 동의를 만들어내지 않음 |
| 후보 선택 | 제시된 대상 중 선택 | 질문 당시 후보와 대응시킴 |
| 누락값 입력 | 실행에 필요한 값 | 사용자가 주지 않은 값을 임의로 보충하지 않음 |
| 권한 응답 | 요청된 권한에 대한 결정 | 단순한 실행 확인과 혼동하지 않음 |

- “첫 번째”는 현재 대기 중인 목록에 해석해야 한다.
- “아니”를 취소로 볼지 값 수정으로 볼지는 질문의 종류와 사용자 의도에 달려 있다.
- 사용자가 새 요청을 시작했다면 이전 실행 참조를 무조건 재사용하지 않는다.
- 기능이 직접 필요한 값을 물을 수 있다면, 어시스턴트가 앞서 불필요한 질문을 만드는지 점검한다.

마지막 항목은 항상 도구부터 호출하라는 규칙이 아니다. 도구가 불완전한 요청을 받을 수 있는지, 실행 없이 입력을 요청할 수 있는지를 계약에서 확인해야 한다.

## 구현을 넘어 운영 상태까지 확인한다

아래는 후속 설계에서 점검할 최소 상태 전이다. 모든 상태를 초기 PoC에서 구현했다는 의미는 아니다.

```text
실행 요청 → 완료
         → 입력 대기 → 유효한 답변 → 실행 재개 → 완료
                    → 취소 → 종료
                    → 만료 → 현재 상태 확인 또는 새 요청
                    → 다른 의도 → 기존 작업과 분리해 처리
```

- **잘못된 참조:** 현재 사용자와 대기 작업에 속한 참조인지 실행 계층에서 검증.
- **중복 응답:** 네트워크 재시도나 중복 입력이 부수 효과를 반복하지 않도록 처리.
- **만료:** 오래된 후보·기기 상태를 그대로 실행하지 않도록 유효성 확인.
- **복수 대기 작업:** 어느 질문에 대한 답변인지 모호하면 추가 확인.

이 경계를 프롬프트에만 맡기면 모델이 잘못 참조했을 때 복구하기 어렵다. 상태의 유효성은 런타임이 확인하고, 언어적 해석은 모델이 맡도록 책임을 나눈다.

## 평가는 질문을 잘했는지에서 끝나지 않는다

| 시나리오 | 검증할 행동 |
| --- | --- |
| 후보 선택 후 “첫 번째” | 원래 목록의 대상과 실행 참조를 유지 |
| 확인 질문 후 “취소해” | 부수 효과 없이 종료 |
| 질문 후 무관한 새 요청 | 이전 작업을 실수로 재개하지 않음 |
| 만료된 요청에 답변 | 실패를 숨기거나 완료를 약속하지 않음 |
| 같은 답변의 재전달 | 실행 서비스의 중복 처리 계약을 따름 |

- 사용자에게 보여 준 질문과 실제 도구 입력을 함께 확인한다.
- 선택된 대상, 호출 참조, 최종 상태를 검증하고 표현 문구의 일치만 보지 않는다.
- 정상 완료뿐 아니라 취소·수정·만료도 회귀 시나리오로 남긴다.

## 적용하면서 얻은 기준

**HITL은 사용자에게 한 번 질문하는 기능보다, 질문 전후의 실행을 정확히 연결하는 구조에 가깝다.**

- 대화 기록, 실행 참조, 대기 상태를 별도의 개념으로 관리한다.
- 사용자가 실제로 답한 범위만 다음 실행에 반영한다.
- 사용자에게는 자연스러운 질문을 제공하고 내부 상태 이름은 노출하지 않는다.
- “완료했습니다”라는 문장보다 실제 작업의 완료 상태를 성공 기준으로 둔다.

이 구조가 필요해진 배경은 [OpenClaw 컴포넌트 적용기의 세션과 실행 참조](/posts/openclaw-component-application/#4-session-context와-business-turn-reference를-분리했다)에서 이어 볼 수 있다.
