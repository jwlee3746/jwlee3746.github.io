**도구가 어떤 행동을 실행할지 정의한다면, Skill은 그 행동을 언제 어떤 순서로 사용할지 설명한다.** 디바이스 어시스턴트에 Skill을 적용하면서 기능의 사용 조건과 작업 절차를 검토 가능한 지침으로 분리할 수 있었다.

하지만 좋은 지침을 작성하는 것만으로는 충분하지 않았다. **모델이 올바른 Skill을 먼저 선택해 읽어야 해당 레시피와 행동 지침도 적용된다.** 하위 에이전트의 기능 경계가 겹치는 요청에서는 이 첫 선택부터 흔들렸다.

이 글은 하위 에이전트의 기능을 Skill로 표현한 초기 구조에서, 요청별 capability를 모델과 하네스에 동적으로 노출하는 구조로 발전시킨 경험을 정리한다. 사례·도표·예시 파일은 공개 가능한 설계 수준으로 일반화했다.

## 도구 스키마만으로는 사용 맥락이 부족했다

메시지 전송 도구는 수신자와 내용을 입력으로 받을 수 있다. 그러나 사용자가 “아까 찾은 사람에게 보내 줘”라고 말했을 때는 이전 결과의 참조, 후보 선택, 필요한 확인까지 함께 다뤄야 한다.

| 계층 | 답해야 하는 질문 | 메시지 작업의 예 |
| --- | --- | --- |
| Tool | 무엇을 입력하면 어떤 행동을 실행하는가? | 수신자·내용을 받아 전송 |
| Skill | 언제 쓰며 어떤 선행 단계가 필요한가? | 후보 조회 → 선택 → 전송 |
| 상태 관리 | 앞선 대화·실행과 어떻게 연결하는가? | 선택한 후보와 대기 중 요청 보존 |
| 실행 정책 | 실제 실행을 허용할 수 있는가? | 권한·입력·중복 실행 검증 |

- 도구 설명에 모든 절차를 넣으면 다른 기능과 공유할 수 있는 지식이 중복된다.
- 전역 프롬프트에 모든 기능의 예외를 넣으면 요청과 무관한 설명도 계속 읽게 된다.
- 초기에는 하위 에이전트별 기능 설명과 호출 절차를 각각 Skill로 구성했다. Skill은 실행 코드 자체가 아니라 **기능을 사용하는 지침**이었다.

## Skill에는 지원 범위와 절차, 제외 조건을 함께 적었다

아래는 절차의 형태만 보여 주는 가상 예시다. 항목 선택이나 확인이 필요한지는 실제 도구 계약과 실행 결과에 따라 결정한다.

```markdown
---
name: message-follow-up
description: 이전 대화에서 찾은 대상을 확인하고 메시지 전송을 이어 간다.
---

## 사용 조건
- 사용자가 메시지 전송을 요청했다.
- 이전 검색 결과를 참조하거나 수신자를 찾아야 한다.

## 절차
1. 사용자 발화와 이전 결과에서 수신자·내용을 확인한다.
2. 후보가 확정되지 않으면 도구가 제공하는 선택 절차를 따른다.
3. 사용자가 선택한 대상과 내용을 보존해 실행한다.
4. 실제 실행 결과를 근거로 완료 여부를 안내한다.

## 제외 조건
- 사용자가 요청하지 않은 수신자나 내용을 임의로 추가하지 않는다.
- 도구가 지원하지 않는 예약 전송을 약속하지 않는다.
```

- `description`에는 검색에 도움이 되는 짧은 사용 조건을 적는다.
- 본문에는 정상 경로뿐 아니라 사용할 수 없는 상황을 적는다.
- 실제 도구와 다른 인자·기능을 요구하지 않는지 함께 검토한다.
- 여러 Skill에 같은 사실을 복사하기보다 공통 지침과 기능별 절차의 책임을 구분한다.

## 문제는 어떤 Skill을 읽을지 결정하는 단계에 있었다

초기 흐름은 사용자 요청을 보고 관련 Skill을 고른 뒤, 본문을 읽고 레시피와 행동 지침을 따르는 방식이었다. 그런데 상세 지침에 도달하려면 먼저 그 Skill을 선택해야 했다.

![요청에서 읽을 Skill을 먼저 선택해야 상세 레시피와 행동 지침에 도달할 수 있는 초기 흐름](/data/images/posts/device-assistant-skills/skill-selection-bottleneck.svg)

- **읽기 전의 판단:** 이 요청에 어떤 Skill이 필요한가?
- **읽은 뒤의 판단:** 지원 범위가 맞는가, 어떤 순서로 실행할 것인가?
- 본문의 레시피는 두 번째 판단을 도와도 첫 선택이 틀리면 활용되지 않는다.
- 다른 기능을 먼저 호출해야 한다는 선행 조건이 본문에만 있으면, 해당 Skill을 읽기 전에는 그 조건도 알기 어렵다.

디바이스 기능을 에이전트별로 나누는 기준과 사용자가 표현하는 목표는 일대일로 대응하지 않았다. 조회·선택·수정을 함께 포함하거나, 비슷한 설명을 가진 기능이 서로 다른 행동을 담당하는 요청에서 경계가 모호해졌다.

| 설명용 요청 | 겹쳐 보이는 기능 | 선택 전에 확인할 내용 |
| --- | --- | --- |
| 내일 회의를 찾아서 오후 3시로 옮겨 줘 | 검색·일정 조회·수정 | 어떤 조회 결과를 어떤 수정 기능에 넘길 것인가? |
| 아까 찾은 사람에게 메시지 보내 줘 | 대상 검색·연락처·메시지 | 이전 결과를 재사용할 수 있는가? |
| 배터리를 오래 쓰도록 설정해 줘 | 기기 설정·최적화·사용법 안내 | 설명을 제공할 기능과 상태를 바꿀 기능 중 무엇이 필요한가? |

위 예시의 실제 담당 기능과 선행 조건은 실행 환경의 capability 계약에 따라 달라진다.

**잘못된 첫 선택은 뒤의 해석과 행동도 제약했다.** 선택한 Skill의 범위에 요청을 맞추거나, 필요한 레시피를 놓치는 문제가 생길 수 있었다. 선택 규칙을 전역 프롬프트에 계속 추가하면 본문과 중복·충돌하고, 모든 Skill을 읽게 하면 무관한 설명까지 늘어난다.

## 요청별 capability를 모델과 하네스에 함께 노출했다

이를 해결하기 위해 요청과 현재 문맥에 맞는 기능 정보를 제공하는 **capability 탐색 계층**을 하네스에 연결했다. capability는 에이전트의 이름을 넘어, **어떤 행동을 지원하며 어떤 제약과 실행 수단을 갖는가**를 표현한다.

![요청에 맞는 capability를 탐색하고 모델의 판단 정보와 하네스의 실행 구성에 함께 반영하는 구조](/data/images/posts/device-assistant-skills/dynamic-capability-exposure.svg)

- 하네스가 요청과 문맥을 바탕으로 관련 capability를 먼저 탐색한다.
- 모델에는 기능 설명, 지원 범위, Skill 후보 등 현재 판단에 필요한 정보를 보여 준다.
- 하네스에는 기능을 분류하고 프롬프트·도구 구성에 반영할 구조화된 정보를 전달한다.
- 필요한 Skill은 본문을 추가로 로드하고, 정보가 부족하면 후속 탐색을 수행한다.
- 실행 결과를 받은 뒤 다음 단계에 필요한 기능과 정보를 다시 판단한다.

**Skill 선택의 출발점을 전체 에이전트 목록에서 요청별 기능 후보로 바꾼 것**이다. 모델의 선택을 없앤 것이 아니라, 선택 전에 읽을 수 있는 근거와 실제 실행 환경을 정렬했다.

| 소비자 | 필요한 정보 | 맡는 책임 |
| --- | --- | --- |
| 모델 | 기능 설명·제약·Skill 후보·로드된 절차 | 사용자 목표에 맞는 다음 행동 판단 |
| 하네스 | 기능 종류·식별 정보·연결할 도구 정의 | 결과 분류, 프롬프트 구성, 필요한 도구 연결 |
| 실행 계층 | 유효한 입력·대상·권한·현재 상태 | 실제 동작 수행과 결과 반환 |

- 같은 탐색 결과라도 모델용 설명과 하네스용 데이터의 표현은 다를 수 있다.
- 설명을 프롬프트에 넣는 경로와 호출 도구를 준비하는 경로를 함께 점검한다.
- 하나의 capability가 반드시 하나의 도구에 대응하지는 않는다. 공통 실행 도구를 공유하거나 여러 단계의 절차를 제공할 수도 있다.
- 탐색됐다는 이유만으로 실행을 허용하지 않는다. 권한과 입력 유효성은 실행 계약에 따라 확인한다.

## 후보 탐색과 상세 Skill 로드의 책임은 유지한다

동적 탐색을 적용한 뒤에도 Skill은 기능별 레시피와 행동 지침을 관리하는 단위로 남는다. 관련 후보를 발견했다는 사실과, 본문의 전체 사용 조건을 확인했다는 사실은 다르다.

![후보 탐색과 Skill 본문 로드, 적합성 판단, 도구 실행, 결과 확인의 흐름](/data/images/posts/device-assistant-skills/skill-discovery.svg)

- **후보 탐색:** 요청과 관련된 기능·Skill을 찾는다.
- **본문 로드:** 선행 조건, 지원 범위, 제외 조건, 작업 절차를 읽는다.
- **적합성 판단:** 도메인 단어가 비슷한지보다 요청한 행동을 실제로 지원하는지 확인한다.
- **실행:** 절차에 따라 호출하고, 결과가 전제를 바꾸면 다시 판단한다.

[Agent Skills 명세](https://agentskills.io/specification)는 `SKILL.md`의 메타데이터와 본문을 구분하고 필요한 정보부터 단계적으로 로드하는 방식을 설명한다. 여기서 다룬 요청별 capability 탐색 계층은 그 명세 자체가 요구하는 구성요소가 아니라, 디바이스 기능 선택 문제를 다루기 위해 추가한 설계다.

| 기준 | 하위 에이전트별 Skill 선택에 의존 | 동적 capability 탐색을 적용 |
| --- | --- | --- |
| 첫 판단의 근거 | 이름·설명으로 읽을 Skill 선택 | 요청·문맥에 맞는 기능 후보를 보고 선택 |
| 경계가 겹치는 요청 | 먼저 고른 Skill 안에서 해석하기 쉬움 | 후보의 행동·제약을 비교할 근거 제공 |
| 상세 레시피 | 선택한 Skill 본문에서 로드 | 필요한 Skill 본문을 상세 로드해 사용 |
| 모델과 실행 환경 | 설명과 도구 구성을 별도로 관리하기 쉬움 | 탐색 결과를 양쪽 구성에 반영 |
| 실패 조사 | 모델의 Skill 선택에 집중 | 탐색·전달·로드·판단·실행으로 분리 |

## 이식 과정에서는 실행 환경에 묶인 가정을 걷어냈다

OpenClaw에서 사용하던 정의를 다른 하네스에 가져오면서, 사용되지 않는 전용 메타데이터와 이름 규칙을 정리했다. 도메인 지식은 재사용할 수 있어도 로더가 해석하는 규칙까지 같지는 않았다.

| 재사용할 지식 | 실행 환경에 맞게 다시 확인할 것 |
| --- | --- |
| 기능의 지원 범위·제약 | front matter 해석과 이름 검증 |
| 필요한 선행 작업 | 실제 등록된 도구 이름·입력 스키마 |
| 후보 선택·후속 실행의 의도 | 상태 참조를 전달하는 방식 |
| 성공·실패를 판단하는 기준 | 도구 결과의 형식과 오류 계약 |

**Skill은 이식 가능한 지식이 될 수 있지만, 파일을 복사하는 것만으로 실행 호환성이 생기지는 않는다.**

## 라우팅 실패를 단계별로 확인한다

후속 적용에서는 검색된 capability가 모델에 전달되기 전 변환 과정에서 누락되는 문제도 다뤘다. 이 경우 모델은 올바른 기능을 선택할 기회 자체를 받지 못한다.

| 단계 | 확인할 질문 |
| --- | --- |
| 탐색 | 요청한 행동을 처리할 기능이 후보에 포함됐는가? |
| 전달 | 분류·병합·필터링 과정에서 후보가 누락되지 않았는가? |
| 상세 로드 | 필요한 레시피와 제외 조건이 모델에게 보였는가? |
| 판단 | 실제 지원 행동을 기준으로 적절한 기능을 골랐는가? |
| 실행 | 하네스가 선택된 기능을 연결하고 올바른 입력으로 실행했는가? |
| 결과 | 목표를 달성하고 요청하지 않은 행동을 추가하지 않았는가? |

- 경계가 겹치는 요청, 범위 밖 요청, 여러 기능을 이어야 하는 요청을 함께 평가한다.
- 정답 capability가 후보에 없는 실패와, 후보에 있는데 잘못 고른 실패를 구분한다.
- 후보가 부족하면 추가 탐색·질문·미지원 안내 중 적절한 행동을 하는지 확인한다.
- 작업을 이어 갈 때는 필요한 정보와 상태를 보존하고, 새 요청에 무관한 후보가 남지 않도록 수명을 관리한다.
- 탐색 지연과 추가 호출 비용도 작업 성공률과 함께 본다.

## 적용하면서 얻은 기준

**레시피를 잘 작성하는 문제와, 그 레시피를 읽어야 하는 시점을 찾아 주는 문제는 서로 다른 설계 과제였다.**

- Skill은 사용 조건과 상세 절차를 검토·교체·평가할 수 있는 단위로 유지한다.
- capability 탐색은 현재 요청에서 판단할 후보와 근거를 드러내는 역할을 맡긴다.
- 하네스는 같은 기능 정보를 모델 입력과 실제 실행 구성에 일관되게 반영한다.
- 모델은 그 근거로 선택·계획하고 부족한 정보를 추가로 확보한다.
- 본문을 읽었다는 사실만으로 성공을 판정하지 않고 실제 행동과 결과를 확인한다.

공개 파일 형식은 [Agent Skills 명세](https://agentskills.io/specification)에서 확인할 수 있다.
