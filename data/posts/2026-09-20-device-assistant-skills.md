**도구가 어떤 행동을 실행할지 정의한다면, Skill은 그 행동을 언제 어떤 순서로 사용할지 설명한다.** 디바이스 어시스턴트에 Skill을 적용하면서 중요했던 것은 기능 설명을 파일로 옮기는 것보다 이 책임을 분리하는 일이었다.

이 글은 [OpenClaw 컴포넌트 적용기](/posts/openclaw-component-application/)의 Skill 경험을 확장한다. 기능 이름과 예시는 설계를 설명하기 위해 일반화했으며, 아래 예시 파일은 실제 서비스의 정의가 아니다.

## 도구 스키마만으로는 사용 맥락이 부족했다

메시지 전송 도구는 수신자와 내용을 입력으로 받을 수 있다. 그러나 사용자가 “아까 찾은 사람에게 보내 줘”라고 말했을 때는 이전 결과의 참조, 후보 선택, 필요한 확인까지 함께 다뤄야 한다.

| 계층 | 답해야 하는 질문 | 메시지 작업의 예 |
| --- | --- | --- |
| Tool | 무엇을 입력하면 어떤 행동을 실행하는가? | 수신자·내용을 받아 전송 |
| Skill | 언제 쓰며 어떤 선행 단계가 필요한가? | 후보 조회 → 선택 → 전송 |
| 상태 관리 | 앞선 대화·실행과 어떻게 연결하는가? | 선택한 후보와 대기 중 요청 보존 |
| 실행 정책 | 실제 실행을 허용할 수 있는가? | 권한·입력·중복 실행 검증 |

- 도구 설명에 모든 절차를 넣으면 다른 기능과 공유할 수 있는 지식이 중복된다.
- 전역 프롬프트에 모든 기능의 예외를 넣으면 요청과 무관한 설명도 계속 읽게 된다.
- Skill을 분리하면 기능별 사용 조건과 제약을 함께 검토할 수 있다.

## 후보 탐색과 상세 지침 로드를 나눈다

관련 있어 보이는 Skill을 발견했다는 사실과, 그 Skill의 전체 사용 조건을 확인했다는 사실은 다르다.

![요청에서 Skill 후보를 탐색하고 본문을 로드한 뒤 범위 확인을 거쳐 도구를 실행하는 흐름](/data/images/posts/device-assistant-skills/skill-discovery.svg)

- **후보 탐색:** 이름과 설명으로 요청과 관련된 Skill을 찾는다.
- **본문 로드:** 후보의 선행 조건, 지원 범위, 제외 조건, 작업 절차를 읽는다.
- **적합성 판단:** 요청을 실제로 처리할 수 있는지 확인한다. 도메인 단어가 같다는 이유만으로 선택하지 않는다.
- **실행:** 절차에 따라 도구를 호출하고, 결과가 전제를 바꾸면 다시 판단한다.

[Agent Skills 명세](https://agentskills.io/specification)는 `SKILL.md`의 메타데이터와 본문을 구분하고, 필요한 정보부터 단계적으로 로드하는 방식을 설명한다. 디바이스 어시스턴트에서도 전체 기능 설명을 항상 펼치는 대신, 탐색과 상세 로드의 역할을 나누는 데 이 구분을 적용할 수 있었다.

## 좋은 Skill은 지원 범위와 제외 조건을 함께 가진다

아래는 절차의 형태만 보여 주는 가상 예시다. 항목 선택이나 확인이 필요한지는 실제 도구 계약과 실행 결과에 따라 결정한다.

```markdown
---
name: message-follow-up
description: 이전 대화에서 찾은 대상을 확인하고 메시지 전송을 이어 간다.
---

## 사용 조건
- 사용자가 메시지 전송을 요청했다.
- 이전 검색 결과를 참조하거나 수신자를 찾아야 한다.

## 절차
1. 사용자 발화와 이전 결과에서 수신자·내용을 확인한다.
2. 후보가 확정되지 않으면 도구가 제공하는 선택 절차를 따른다.
3. 사용자가 선택한 대상과 내용을 보존해 실행한다.
4. 실제 실행 결과를 근거로 완료 여부를 안내한다.

## 제외 조건
- 사용자가 요청하지 않은 수신자나 내용을 임의로 추가하지 않는다.
- 도구가 지원하지 않는 예약 전송을 약속하지 않는다.
```

- `description`은 검색에 도움을 주는 짧은 사용 조건으로 작성한다.
- 본문에는 정상 경로뿐 아니라 사용할 수 없는 상황을 적는다.
- 자주 바뀌는 사실을 여러 Skill에 복사하면 어느 문서가 최신인지 판단하기 어려워진다.
- Skill이 실제 도구와 다른 인자·기능을 요구하지 않는지 함께 검토한다.

## 이식 과정에서는 실행 환경에 묶인 가정을 걷어냈다

OpenClaw에서 사용하던 정의를 다른 하네스에 가져오면서, 사용되지 않는 전용 메타데이터와 이름 규칙을 정리했다. 도메인 지식은 재사용할 수 있어도 로더가 해석하는 규칙까지 같지는 않았다.

| 재사용할 지식 | 실행 환경에 맞게 다시 확인할 것 |
| --- | --- |
| 기능의 지원 범위·제약 | front matter 해석과 이름 검증 |
| 필요한 선행 작업 | 실제 등록된 도구 이름·입력 스키마 |
| 후보 선택·후속 실행의 의도 | 상태 참조를 전달하는 방식 |
| 성공·실패를 판단하는 기준 | 도구 결과의 형식과 오류 계약 |

**Skill은 이식 가능한 지식이 될 수 있지만, 파일을 복사하는 것만으로 실행 호환성이 생기지는 않는다.**

## 라우팅 실패를 프롬프트 탓으로만 보지 않는다

후속 적용에서는 검색된 capability가 모델에게 전달되기 전 변환 과정에서 누락되는 문제도 다뤘다. 이 경우 모델은 올바른 기능을 선택할 기회 자체를 받지 못한다.

- **검색 단계:** 관련 Skill이 후보에 있었는가?
- **전달 단계:** 후보와 도구별 capability가 병합·필터링 과정에서 사라지지 않았는가?
- **로드 단계:** 본문과 제외 조건까지 읽었는가?
- **선택 단계:** 읽은 내용을 근거로 적절한 기능을 선택했는가?
- **실행 단계:** 도구가 요청대로 실행됐고 결과를 정확히 해석했는가?

이 단계를 나눠 관측하면 검색 품질, 데이터 변환 오류, 모델의 판단 오류를 서로 다른 문제로 다룰 수 있다.

## 적용하면서 얻은 기준

**Skill의 가치는 기능 수를 늘리는 데 그치지 않고, 기능을 사용하는 지식을 검토·교체·평가 가능한 단위로 만드는 데 있다.**

- 본문이 로드됐다는 사실만으로 실행 성공을 판정하지 않는다.
- 허용 도구 표기는 하네스가 해석·강제할 때 의미가 있다. 자연어 지침만으로 권한을 통제하지 않는다.
- 짧고 단순한 기능까지 무조건 별도 Skill로 만들기보다, 분리할 사용 조건이나 절차가 있는지 먼저 확인한다.
- 정상 요청, 범위 밖 요청, 후보가 모호한 요청을 함께 평가한다.

관련 설계의 출발점은 [OpenClaw 컴포넌트 적용기](/posts/openclaw-component-application/), 공개 파일 형식은 [Agent Skills 명세](https://agentskills.io/specification)에서 확인할 수 있다.
