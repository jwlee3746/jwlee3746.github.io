**디바이스 어시스턴트의 프롬프트는 역할 지침, 현재 사용할 수 있는 기능, 진행 중인 실행 상태를 함께 표현해야 한다.** 이 세 가지의 변경 주기가 다르다는 점이 하네스 설계의 출발점이었다.

이 글은 [OpenClaw 컴포넌트 적용기](/posts/openclaw-component-application/)에서 다룬 경험 중 프롬프트 구성 문제를 확장한 기록이다. 사례와 도표는 공개 가능한 설계 수준으로 일반화했으며, 아래 조립 절차는 설명을 위한 예시다.

## 하나의 프롬프트에 서로 다른 수명의 정보가 들어갔다

디바이스 어시스턴트는 같은 발화라도 현재 기기, 검색된 기능, 앞선 실행 결과에 따라 다른 행동을 해야 한다. 그런데 이 정보를 하나의 긴 시스템 프롬프트로 관리하면 무엇을 언제 갱신해야 하는지 흐려진다.

| 정보 | 예시 | 바뀌는 시점 | 관리 책임 |
| --- | --- | --- | --- |
| 역할과 판단 원칙 | 사용자의 의도와 제약을 보존 | 제품 정책 변경 | 역할 지침 |
| 도구 사용 지침 | 언제 호출하고 무엇을 기다리는가 | 도구 계약 변경 | 도구 지침 |
| 호출 가능한 기능 | 이번 요청에 검색된 capability | 요청·탐색 단계 | 하네스 |
| 대화와 실행 상태 | 이전 실행의 결과, 확인 대기 | 실행 단계·사용자 응답 | 상태 관리 계층 |

- 정책은 그대로인데 capability 목록만 달라지는 요청이 있다.
- 도구 이름은 같아도 런타임이 바뀌면 입력 스키마와 지원 범위가 달라질 수 있다.
- 이전 턴의 기능 설명을 계속 남기면 현재 사용할 수 없는 기능까지 선택 후보처럼 보일 수 있다.

## 파일 분리와 동적 주입은 서로 다른 작업이다

`AGENTS.md`와 `TOOLS.md`로 나누는 것은 **지침의 책임을 분리하는 일**이다. 요청마다 필요한 capability와 상태를 조합하는 것은 **하네스가 수행하는 실행 작업**이다.

![역할 지침과 도구 지침, 요청별 capability와 실행 상태가 하네스를 거쳐 모델 입력으로 조립되는 구조](/data/images/posts/device-assistant-prompt-harness/prompt-assembly.svg)

- `AGENTS.md`: 역할, 의도 해석, 다음 행동을 선택하는 원칙.
- `TOOLS.md`: 도구 선택 조건, 인자 작성 원칙, 결과에 따른 후속 행동.
- 요청별 capability: 현재 발견한 기능의 범위와 사용 조건.
- 실행 상태: 이전 결과, 확인 대기 여부, 현재 단계에 필요한 문맥.
- 하네스: 이 정보를 선택·배치하고 실제 도구 스키마와 함께 모델에 전달하는 실행 코드.

[OpenClaw의 workspace 문서](https://docs.openclaw.ai/concepts/agent-workspace)는 운영 지침과 환경 정보를 파일로 관리하는 구조를 설명한다. 여기서 가져온 것은 지침을 명시적으로 관리하는 방식이다. 이 글의 파일 분할과 요청별 조립 구조 전체가 OpenClaw의 현재 기본 동작이라는 뜻은 아니다.

## 적용 과정에서 드러난 문제는 지침과 실행 계약의 불일치였다

기존 지침을 새 하네스로 옮기면서, 프롬프트가 요구하는 인자와 실제 도구 스키마가 맞지 않는 경우를 확인했다. 반복 실행을 전제로 쓴 설명을 제한된 예약 도구에 그대로 적용하는 문제도 있었다.

| 불일치 | 모델에 보이는 상황 | 고쳐야 할 지점 |
| --- | --- | --- |
| 지침에만 존재하는 인자 | 작성하라는 값이 호출 스키마에 없음 | 지침과 스키마의 계약 정렬 |
| 지원하지 않는 예약 방식 | 할 수 있다고 읽었지만 실행 수단이 없음 | 지원 범위와 대안 안내 |
| 이전 기능 목록 잔존 | 현재도 호출 가능한 것처럼 보임 | 요청별 주입 범위와 수명 |
| 내부 이름을 포함한 예시 | 사용자에게 구현 이름을 설명 | 내부 판단과 사용자 표현의 분리 |

**파일을 잘 나누는 것만으로 불일치가 사라지지는 않는다.** 도구의 실제 입력과 지원 범위를 기준으로 지침을 다시 읽어야 했다.

## 조립 결과를 하나의 검증 대상으로 본다

아래는 조립 경계를 설명하는 의사 코드다. 실제 구현이나 특정 라이브러리 API를 옮긴 코드는 아니다.

```text
role     = load_role_instructions(revision)
guidance = load_tool_guidance(revision)
tools    = resolve_callable_tools(request_context)
caps     = discover_relevant_capabilities(request)
state    = restore_execution_state(conversation)

prompt = compose(role, guidance, caps, state)
validate_contract(prompt, tools)
invoke_model(prompt, tools)
```

- **정적 검사:** placeholder 누락, 등록되지 않은 도구 참조, 필수 섹션 누락을 확인.
- **스냅샷 검사:** capability가 의도한 섹션에 들어가는지, 이전 요청의 정보가 남지 않는지 확인.
- **행동 평가:** 동일 발화에서 호출 도구·인자·추가 질문·사용자 안내가 어떻게 바뀌는지 확인.
- **변경 추적:** 역할 지침, 도구 지침, capability 정의의 버전을 구분해 기록.

자연어 지침의 모든 모순을 정적으로 검출할 수는 없다. 스냅샷이 같아도 모델 행동은 바뀔 수 있으므로 구조 검사와 행동 평가를 함께 둔다.

## 동적으로 넣는 정보에도 경계가 필요하다

- 기능 설명을 주입했다고 실행 권한이 생기는 것은 아니다. 권한과 인자 검증은 실행 계층의 책임이다.
- 검색 결과와 사용자 데이터는 운영 지침을 덮어쓰는 명령으로 취급하지 않는다.
- 필요한 본문을 너무 적게 남기면 제약을 놓치고, 너무 많이 남기면 현재 판단에 중요한 정보가 묻힌다.
- 정의 파일을 배포 시 읽는지 요청마다 다시 읽는지는 별도 구현 선택이다. 동적 주입이 곧 파일 변경의 즉시 반영을 뜻하지 않는다.

## 적용하면서 얻은 기준

**프롬프트를 관리한다는 것은 모델이 읽을 문자열뿐 아니라, 그 문자열을 언제 어떤 실행 계약과 함께 보여 줄지 관리하는 일이다.**

- 고정 지침과 요청별 정보를 분리해 각각의 변경 이유를 설명할 수 있게 한다.
- 지원 기능의 사실은 도구 계약에서, 판단 순서는 지침에서 관리해 중복을 줄인다.
- 파일 원문과 함께 실제 조립 결과를 검토한다.
- 잘못된 호출을 발견하면 프롬프트, 주입 데이터, 실행 스키마 중 어느 경계에서 어긋났는지 먼저 확인한다.

관련 경험의 전체 맥락은 [OpenClaw 컴포넌트 적용기](/posts/openclaw-component-application/)에 정리했다.
